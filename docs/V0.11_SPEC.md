## V0.10.5 Changes

V0.10.5 was a stabilization release addressing all known issues from V0.10. These fixes are the prerequisite for the V0.11 benchmark.

### KI-10: CancellationToken Not Propagated Through Pipeline

**Severity:** Critical
**Fix:** CancellationToken now flows through the entire action pipeline — from `AgentOrchestrator` through `ActionExecutor` to individual `IActionHandler` implementations. Long-running OCR and screenshot operations respect cancellation and terminate promptly.

### KI-11: LLM Fallback Silently Swallows Errors Without Warning

**Severity:** High
**Fix:** When the primary LLM provider fails and the system falls back to an alternative, a structured warning is now emitted via the trace pipeline and logged at `Warning` level. The caller receives a non-null `FallbackWarning` object in the response metadata.

### KI-12: Sync Wrappers Block the Async Pipeline

**Severity:** High
**Fix:** All synchronous wrappers around async operations have been removed. Call sites now use `await` directly. Deadlock-prone `.Result` and `.Wait()` calls have been eliminated from the hot path.

### KI-13: Test Projects Not Included in Solution File

**Severity:** Medium
**Fix:** All test projects are now included in `PeekabooWin.sln`. `dotnet test` runs the full suite from the solution root without additional configuration.

### KI-4: OCR Engine Not Set to Default When No Config Provided

**Severity:** Medium
**Fix:** When no OCR engine is specified in configuration, the system defaults to `WindowsAiOcr` on Windows 10+ and `Tesseract` as fallback. The default is applied at `OcrEngineFactory` creation time.

### KI-5: OCR Errors Not Surfaced to Caller

**Severity:** Medium
**Fix:** OCR failures now propagate through `OcrResult` with structured error information including `ErrorCode`, `Message`, and `Hint`. Callers can distinguish between "no text found" and "engine failure" and take appropriate recovery action.

## V0.11 Benchmark Framework

### RealDesktop-30

RealDesktop-30 is a 30-case benchmark suite covering 10 categories of real-world Windows desktop automation scenarios. Each case defines a task, expected outcome, and safety boundary.

**Design principles:**
- Tasks are representative of actual agent workloads (window management, file operations, dialog interaction, etc.)
- Safety boundaries are explicit — any action crossing a boundary is flagged by ActionRiskGate
- Grounding quality is measured per-action using ElementGroundingScore
- Skill reuse is tracked — a skill recorded in an earlier case may be replayed in a later case

**Category list:**

1. Window Management
2. Menu Navigation
3. Text Input & Editing
4. File Explorer Operations
5. Dialog Interaction
6. Multi-Window Workflow
7. System Tray & Notifications
8. Drag & Drop
9. Accessibility Tree Navigation
10. Error Recovery & Retry

## API Evolution Roadmap

PeekabooWin is evolving from a "can call" library to an **agent-hostable** runtime.

### Phase 1 — "Can Call" (V0.10)
- Library consumed via C# API
- Caller manages the agent loop
- No structured trace output
- No risk gate

### Phase 2 — "Can Call + Trace" (V0.10.5)
- VacpTraceRecord emitted per action
- ActionRiskGate introduced
- CancellationToken propagation
- Error surfacing

### Phase 3 — "Agent-Hostable" (V0.11)
- HTTP API endpoints for agent integration
- Structured API response envelope (request_id, trace_id, status, decision, data, error, hint)
- Trace schema published and versioned
- SkillReplayEngine for skill reuse across sessions

### Phase 4 — "Trusted Runtime" (V1.0, planned)
- Policy engine for configurable safety rules
- Multi-agent session isolation
- Audit log persistence and export
- Plugin architecture for custom action handlers

## V1.0 Positioning

**PeekabooWin: A Trusted Visual Desktop Automation Runtime for Windows Agents**

V0.11 establishes the evidence base for V1.0. The key positioning pillars are:

1. **Trusted** — Every action passes through ActionRiskGate; decisions are recorded in an immutable trace; catastrophic unsafe actions are zero.
2. **Visual** — OCR, screenshot, and accessibility tree integration provide multi-modal desktop understanding.
3. **Desktop Automation** — Purpose-built for Windows desktop scenarios, not a general-purpose automation framework.
4. **Runtime** — Agent-hostable API, structured error handling, skill replay, and verification make PeekabooWin a runtime, not just a library.
5. **For Windows Agents** — The target consumer is an AI agent (LLM-based or rule-based) that needs to interact with the Windows desktop safely and reliably.

V1.0 will add policy engine, multi-agent isolation, audit log persistence, and plugin architecture — completing the transition from "automation library" to "trusted runtime."
